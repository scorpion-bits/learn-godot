A pergunta parece boba. A resposta define a arquitetura do seu jogo.

E tem um ganho que não é técnico Com os itens virando arquivos, quem cria conteúdo não precisa saber programar. Numa equipe como a de vocês, isso significa que a pessoa de arte ou de game design consegue inventar um item novo sem abrir um script.
04 · Conceito

NODE GUARDA COMPORTAMENTO. RESOURCE GUARDA DADO.

A segunda família de peças do Godot

Node

Existe dentro da cena. Ocupa lugar na árvore, roda _process, aparece na tela. É um ator do jogo.

Resource

Existe como arquivo. Não tem posição, não roda a cada frame, não aparece sozinho. É uma ficha de dados que qualquer Node pode carregar.

Você já usou Resources sem perceber A Texture2D que você arrastou para o Sprite2D é um Resource. O RectangleShape2D do CollisionShape2D também. A animação que você gravou no AnimationPlayer também. Todo esse tempo você estava preenchendo fichas de dados.
Uma analogia O Node é o garçom: anda pelo salão, faz coisas. O Resource é o cardápio: não faz nada sozinho, mas todo mundo consulta, e existe um só para o restaurante inteiro.
O detalhe que pega Um Resource é compartilhado. Se dez poções no mapa apontam para o mesmo arquivo e você mudar um campo dele em tempo de execução, as dez mudam juntas. Hoje isso é o que queremos; guarde a informação para quando não for.
05 · Prática

CRIANDO O ITEMDATA

Sete linhas que definem o que é um item no seu jogo

ItemData.gd
●●●
extends Resource
class_name ItemData

@export var name : String = "Item"
@export var icon : Texture2D
@export_multiline var description : String = ""
extends Resource, não Node É essa linha que faz a diferença. Sem ela você teria mais um Node, que só existe dentro de uma cena. Com ela, você ganha algo que vira arquivo.
O class_name de novo Mesma função dos componentes: registra ItemData como um tipo do projeto. É por causa dele que daqui a pouco vamos poder escrever @export var data : ItemData e o Godot já saber o que esperar.
@export_multiline É o @export de sempre, só que o Inspector mostra uma caixa de texto de várias linhas em vez de uma linha só. Detalhe pequeno que faz diferença para quem vai escrever a descrição.

CADA ITEM VIRA UM ARQUIVO

A partir daqui, criar item é preencher formulário — não é programar

  1. No painel FileSystem, clique com o botão direito numa pasta → New Resource…
  2. Na busca, digite ItemData — ele aparece na lista porque demos um class_name.
  3. Salve como potion.tres, dentro de uma pasta items/.
  4. Clique no arquivo criado: o Inspector mostra os três campos. Preencha.
O que é um .tres? É o arquivo de Resource do Godot em formato de texto. Pode abrir num editor de texto e ler — e, porque é texto, funciona bem com controle de versão quando várias pessoas mexem no mesmo projeto.

07 · Game Design

POUCOS ITENS, CADA UM IMPORTA

Antes de programar a mochila, uma decisão que muda o jogo inteiro

O inventário que você gerencia

Dezenas de espaços, arrastar, empilhar, organizar. Existe em jogos que são sobre carregar carga — sobrevivência, mineração, loja. O jogador passa tempo real arrumando a bolsa, e isso é a diversão.

O inventário que você usa

Quatro espaços, nada de arrastar. Cada item resolve numa tecla. Existe em jogos que são sobre agir — ação, aventura, exploração. Abrir a mochila leva dois segundos e você volta a jogar.

O jogo de vocês é do segundo tipo Um top-down de ação. Se o jogador estiver organizando bolsa, ele não está fazendo aquilo que o seu jogo faz de melhor. Escolher poucos slots não é preguiça — é escolher onde a atenção dele vai.

É esta a mochila que vamos construir. Cabe inteira na tela, sem rolagem, e o jogador entende de relance:

E olha o que some do seu trabalho Sem arrastar e soltar, sem empilhar, sem ordenar, sem rolagem. Quatro slots fixos é a versão que você consegue terminar hoje — e que continua boa depois.

Uma cena só, que se transforma em qualquer item

Repare no que não vamos fazer: uma cena para a poção, outra para a chave, outra para a espada. É uma cena só. O que muda é o ItemData que ela recebe na gaveta do Inspector.

extends Area2D
class_name WorldItem

@export var data : ItemData

@onready var sprite : Sprite2D = $Sprite2D

func _ready() -> void:

10 · Prática

COLETANDO AO ENCOSTAR

O Signal que você viu em Colisores, agora com um propósito

O Area2D dispara o signal body_entered quando um corpo entra nele. Conectamos esse signal a uma função nossa e, dentro dela, entregamos o dado ao inventário de quem encostou.

Repare em quem conhece quem O item não guarda uma referência ao player. Ele reage a quem entrou nele, seja o player, seja outra coisa. Isso é o que mantém as peças soltas umas das outras.
Por que get_node_or_null e não get_node? Porque quem encostou pode não ter inventário nenhum — um inimigo, uma caixa. O get_node derruba o jogo com erro nesse caso; o _or_null devolve null e a gente decide o que fazer.
WorldItem.gd — continuação
●●●
# conectado ao signal body_entered do Area2D
func _on_body_entered(body : Node2D) -> void:
    var inventory = body.get_node_or_null("InventoryComponent")

    if(!inventory):
        return   # quem encostou não coleta itens

    if(inventory.add_item(data)):
        queue_free()   # só some se coube
O item só desaparece se realmente foi guardado Por isso o add_item devolve true ou false. Se a mochila estiver cheia, o item continua no chão em vez de sumir no nada — que é o tipo de bug que o jogador percebe e odeia.
11 · Prática

O INVENTORY COMPONENT

Mais um Node vazio com um script — e por dentro, um Array

InventoryComponent.gd
●●●
extends Node
class_name InventoryComponent

# avisa quem estiver interessado que a lista mudou
signal changed

@export var max_slots : int = 4

var items : Array[ItemData] = []

func add_item(item : ItemData) -> bool:
    if(items.size() >= max_slots):
        return false

    items.append(item)
    changed.emit()
    return true

func remove_item(item : ItemData) -> void:
    items.erase(item)
    changed.emit()
Array[ItemData] — um Array com tipo É o mesmo Array do Módulo 2, só que dizendo o que pode entrar. Se alguém tentar guardar um número aqui, o Godot avisa na hora em vez de deixar o erro aparecer só na hora de desenhar a interface.
Criando o seu próprio Signal Até agora você só usou signals que o Godot oferecia. signal changed cria um novo, e changed.emit() dispara. O inventário não sabe que existe uma interface — ele só grita "mudei!" e quem quiser que escute.
Por que add_item devolve bool? Para quem chamou saber se deu certo. Com 4 slots, a mochila enche rápido — e é essa resposta que faz o item continuar no chão em vez de sumir no nada.

A MOCHILA MORA FORA DA CENA

Uma interface só para o jogo inteiro — e o jogo pausa enquanto ela está aberta

Como Autoload, a mochila nasce com o jogo e é alcançável de qualquer script: InventoryUI.open(inventory).

Project Settings — Globals ▸ Autoload
Autoload
Path res://ui/InventoryUI.tscn
Node Name InventoryUI
O nome em Node Name é o nome da variável Registre como Inventory_UI e o InventoryUI.open(...) deixa de existir.
E some o caminho relativo Sem Autoload, o Player acharia a mochila por get_node("../../CanvasLayer/HUD") — que quebra ao mover a cena.
● ● ● 
# InventoryUI.gd — raiz CanvasLayer
extends CanvasLayer

var current : InventoryComponent = null

func open(inventory : InventoryComponent) -> void:
    current = inventory
    inventory.changed.connect(redraw)
    redraw()
    show()
    get_tree().paused = true
func close() -> void:
    # a mochila é eterna, o inventário não
    if(current):
        current.changed.disconnect(redraw)

    current = null
    hide()
    get_tree().paused = false
Marque Process Mode ▸ Always na raiz Senão a mochila pausa junto com o jogo e não responde a clique — igual ao menu de pausa do Módulo 7.
15 · Prática

OS SLOTS SE REDESENHAM SOZINHOS

A interface se inscreve uma vez e nunca mais precisa perguntar nada

InventoryUI.gd — continuação
●●●
@onready var slots : HBoxContainer = $Panel/Slots

func redraw() -> void:
    for child in slots.get_children():
        slots.remove_child(child)
        child.queue_free()

    for item in current.items:
        var slot = TextureButton.new()
        slot.texture_normal = item.icon
        slot.tooltip_text = item.name
        slot.custom_minimum_size = Vector2(48, 48)
        slot.pressed.connect(current.use_item.bind(item))
        slots.add_child(slot)
Aqui está o pagamento do signal A interface se inscreve uma única vez, lá no open(). Coletou item? O inventário grita changed e os slots se refazem. A mochila nunca precisa ficar perguntando "mudou alguma coisa?" a cada frame.
Por que remove_child e queue_free? O queue_free marca o Node para morrer no fim do frame — ele ainda está lá nas linhas seguintes. O remove_child tira da árvore na hora, evitando que os slots velhos apareçam junto com os novos por um instante.
.bind(item) — a novidade da linha O signal pressed não carrega informação nenhuma: só diz "clicaram". O bind gruda um argumento na função antes de conectar, então cada botão já sabe qual item é o seu. Sem isso, os quatro slots chamariam a mesma função sem saber em quem clicaram. O use_item a gente escreve daqui a dois slides.

17 · Prática

O EFEITO TAMBÉM É UM ARQUIVO

Um Resource que, em vez de guardar dado, guarda o que fazer

● ● ● 
# ItemEffect.gd — não faz nada de propósito
extends Resource
class_name ItemEffect

func apply(user : Node) -> void:
    pass   # cada efeito preenche do seu jeito
# SpeedEffect.gd
extends ItemEffect
class_name SpeedEffect

@export var bonus : float = 120.0
@export var duration : float = 5.0

func apply(user : Node) -> void:
    var movement = user.get_node("MovementComponent")
    movement.max_speed += bonus
    await user.get_tree().create_timer(duration).timeout
    movement.max_speed -= bonus
# ItemData.gd ganha uma linha
@export var effect : ItemEffect

# InventoryComponent.gd — o if inteiro virou isto
func use_item(item : ItemData) -> void:
    if(!item.effect):
        return   # item que não faz nada, tudo bem

    item.effect.apply(get_parent())
    remove_item(item)
É a mesma jogada do ItemData, um andar acima Lá, "o que é o item" virou arquivo. Aqui, "o que o item faz" vira arquivo. O InventoryComponent não precisa conhecer efeito nenhum: ele pede apply() e o arquivo sabe o resto.
Criar um efeito novo não toca em nada existente BombEffect.gd é um arquivo novo com o seu próprio apply(). Arraste no campo Effect da bomba e acabou. O use_item continua com as cinco linhas dele para sempre.
await — a palavra nova Ela pausa esta função até o cronômetro terminar, sem travar o resto do jogo. As linhas depois dela rodam 5 segundos mais tarde. É assim que o bônus vai embora sozinho, sem você guardar contador nenhum.

LARGANDO DE VOLTA NO CHÃO

O caminho de volta, com a mesma cena que você já construiu

InventoryComponent.gd — continuação
●●●
@export var world_item_scene : PackedScene

func drop_item(item : ItemData) -> void:
    var dropped = world_item_scene.instantiate()

    # o dado entra ANTES de entrar na árvore
    dropped.data = item
    dropped.global_position = get_parent().global_position \
        + Vector2(0, 28)

    get_tree().current_scene.add_child(dropped)
    remove_item(item)
Nenhuma cena nova É o mesmo WorldItem do começo da aula. Ele já sabe se desenhar a partir do data que recebe — então largar uma chave e largar uma poção é exatamente o mesmo código.
Por que a ordem importa O _ready() do WorldItem só roda quando ele entra na árvore, no add_child. Se você mandar o data depois disso, o _ready já rodou sem dado, deu push_error e o item aparece invisível.
E o Vector2(0, 28)? Largue o item exatamente em cima do jogador e ele é coletado de novo no mesmo instante — o item pisca e volta para a mochila. Empurrar um pouco para baixo resolve, e é o tipo de bug que só aparece testando.
