01 · Boas-vindas

BATALHAS POR TURNO

Atacar, defender ou fugir — e o jogo esperando você decidir

Antes de começar Você já tem tudo que uma batalha precisa: player e inimigo com LifeComponent, e um jeito de causar dano. Hoje não vamos criar peça nova de combate — vamos criar o árbitro que organiza o confronto.
02 · Roteiro

Uma batalha completa, no espírito dos RPGs clássicos

Fazer o jogo esperarPela primeira vez o jogo para e não faz nada até você escolher.
Controlar de quem é a vezCom enum — um jeito de dar nome aos estados do jogo.
Três açõesAtacar, defender e fugir — cada uma com uma consequência diferente no turno.
Dar ritmo com awaitPara o inimigo não jogar no mesmo instante em que você clica.
Uma IA honestaSimples de propósito — e você vai ver que já é suficiente.
Encerrar a batalhaVitória, derrota ou fuga, cada uma com o seu caminho.
Repare no que NÃO vamos construir hoje Nada de vida nova, nada de sistema de dano novo. O LifeComponent do módulo passado entra aqui sem uma linha de mudança. Quando uma peça bem feita atravessa um módulo inteiro intacta, é sinal de que ela foi bem desenhada.
03 · Conceito

A MUDANÇA MAIS ESTRANHA ATÉ AQUI

Durante dez módulos o jogo nunca parou. Agora ele vai parar.

Tudo que você fez até hoje roda sozinho

O _physics_process acontece 60 vezes por segundo, tenha você apertado algo ou não. O personagem anda, a física calcula, a animação toca. O jogo nunca espera.

Numa batalha por turno, o jogo congela

Ele mostra as opções e não faz absolutamente nada até você clicar. Depois age, e congela de novo. O tempo do jogo passa a ser o tempo da sua decisão.

Por que isso importa como design Quando o jogo espera, o jogador tem tempo de pensar. É por isso que jogos de turno conseguem ser estratégicos com regras simples: a dificuldade está na escolha, não no reflexo.
Como se faz um jogo "esperar"? Não é com um comando de pausa. É guardando numa variável de quem é a vez e recusando qualquer ação que chegue fora dela. O jogo continua rodando — ele só passa a ignorar quase tudo.
E o teclado? Nesta aula o jogador escolhe clicando em botões — os Button da aula de Interface. O InputComponent continua existindo para o mapa; ele só não manda na batalha.
04 · Fundamentos

DANDO NOME AOS ESTADOS: ENUM

Um tipo novo, e o mais fácil de todos

Precisamos guardar de quem é a vez. Dá para usar um número (0 = player, 1 = inimigo), mas três meses depois ninguém lembra o que era 1. O enum resolve isso: cria uma lista fechada de opções com nome.

o problema
●●●
var turn = 1   # 1 é o quê mesmo?

if(turn == 2):   # e 2 existe?
a solução
●●●
enum State { PLAYER_TURN, ENEMY_TURN, OVER }

var state : State = State.PLAYER_TURN

if(state == State.ENEMY_TURN):
    # dá pra ler em voz alta
Por baixo continuam sendo números PLAYER_TURN vale 0, ENEMY_TURN vale 1, OVER vale 2 — o Godot numera sozinho, na ordem. A diferença é só para o leitor humano. E é uma diferença enorme.
MAIÚSCULAS por convenção Valores de enum se escrevem em maiúsculas com underline, como PLAYER_TURN. É o mesmo tipo de acordo do tudo_minusculo para funções: ninguém é obrigado, todo mundo faz.
05 · Prática

O BATTLE MANAGER — O ÁRBITRO

Ele não luta. Ele decide de quem é a vez e o que vale.

BattleManager.gd
●●●
extends Node
class_name BattleManager

enum State { PLAYER_TURN, ENEMY_TURN, OVER }

signal turn_changed(new_state : State)
signal battle_ended(result : String)

@export var player_life : LifeComponent
@export var enemy_life : LifeComponent

@export var player_damage : int = 2
@export var enemy_damage : int = 2

var state : State = State.PLAYER_TURN
var player_defending : bool = false
Os dois LifeComponent chegam por @export Exatamente como o body do MovementComponent lá atrás. O árbitro não procura ninguém na cena: recebe os dois lutadores arrastados no Inspector.
Repare que ele não tem vida nem dano próprios A vida está nos componentes; o dano é uma configuração da batalha. O árbitro é só regra — e por isso cabe num arquivo pequeno.
Por que player_defending não é @export? Mesma regra do módulo passado: @export é configuração, variável comum é estado. Defender é algo que acontece durante a luta.
06 · Prática

AS TRÊS AÇÕES DO JOGADOR

Repare na primeira linha das três — é a mesma

BattleManager.gd — ações
●●●
func player_attack() -> void:
    if(state != State.PLAYER_TURN):
        return

    enemy_life.take_damage(player_damage)
    end_player_turn()

func player_defend() -> void:
    if(state != State.PLAYER_TURN):
        return

    player_defending = true
    end_player_turn()

func player_flee() -> void:
    if(state != State.PLAYER_TURN):
        return

    if(randf() < 0.5):
        state = State.OVER
        battle_ended.emit("fled")
    else:
        end_player_turn()   # falhou: perdeu a vez
A primeira linha é a trava if(state != State.PLAYER_TURN): return aparece nas três de propósito. É ela que garante que nada acontece fora da vez — mesmo que um botão fique clicável por engano, mesmo que alguém chame a função de outro lugar.
randf() Devolve um número aleatório entre 0 e 1. Comparar com 0.5 é o mesmo que jogar uma moeda: metade das vezes dá certo. Troque para 0.3 e fugir vira difícil; para 0.9, quase garantido.
Fugir tem preço Se falhar, o turno passa mesmo assim e o inimigo ataca de graça. Sem esse risco, fugir seria sempre a melhor jogada — e uma opção que é sempre certa deixa de ser uma escolha.
07 · Prática

DEFENDER — E UMA VELHA CONHECIDA

Aquela pegadinha do Módulo 2 volta, e agora ela quebra o jogo de verdade

BattleManager.gd — dano recebido
●●●
var damage = enemy_damage

if(player_defending):
    damage = damage / 2

    # divisão de int por int descarta o decimal!
    # sem isto, defender contra dano 1 daria 0
    if(damage < 1):
        damage = 1

player_life.take_damage(damage)
player_defending = false   # vale um turno só
Lembra do 5 / 2 = 2? Lá no Módulo 2 isso era curiosidade. Aqui é um bug de verdade: com dano 1, 1 / 2 dá 0, e defender deixaria o jogador invulnerável. A turma que testar vai descobrir sozinha — e vai ser a melhor lição da aula.
A última linha é a que faz defender ser uma escolha player_defending = false zera a proteção depois de usada. Sem ela, defender uma vez protegeria para sempre e o jogador nunca mais precisaria escolher nada.
Quando defender vale a pena? Se defender só reduz o dano, atacar é quase sempre melhor — porque encurta a luta. Defender fica interessante quando existe algo mais a ganhar com o tempo: um veneno que passa, uma poção que dá para tomar. Guarde isso para quando for balancear.

09 · Prática

O TURNO DO INIMIGO

E o comando que faz o jogo respirar

BattleManager.gd — turnos
●●●
func end_player_turn() -> void:
    if(enemy_life.life == 0):
        state = State.OVER
        battle_ended.emit("victory")
        return

    state = State.ENEMY_TURN
    turn_changed.emit(state)
    enemy_turn()

func enemy_turn() -> void:
    # espera 1 segundo antes de agir
    await get_tree().create_timer(1.0).timeout

    # ... aplica o dano (slide anterior) ...

    if(player_life.life == 0):
        state = State.OVER
        battle_ended.emit("defeat")
        return

    state = State.PLAYER_TURN
    turn_changed.emit(state)
await — a função pausa e continua depois Ela para exatamente naquela linha, deixa o jogo seguir, e retoma quando o cronômetro de 1 segundo termina. É a primeira vez no curso que uma função sua não roda de uma vez só.
Esse segundo não é enfeite Sem ele, você clica em atacar e leva o contra-ataque no mesmo instante — parece um bug. A pausa é o que deixa o jogador ler o que aconteceu. Em jogo de turno, ritmo é metade da experiência.
A checagem de morte vem antes de passar a vez Se o inimigo morreu, a batalha acaba ali — ele não pode revidar depois de derrotado. Trocar a ordem dessas linhas é um bug clássico e difícil de perceber.
10 · Conceito

A IA MAIS SIMPLES QUE FUNCIONA

O inimigo desta aula sempre ataca. E tudo bem.

"IA" soa grande, mas num jogo de turno ela é só isto: uma função que escolhe uma ação. A nossa escolhe sempre a mesma — e é o suficiente para a batalha funcionar e ser testável.

Comece burro de propósito Um inimigo previsível deixa você conferir se as regras estão certas. Só depois que a batalha estiver funcionando é que vale torná-lo esperto — senão você não sabe se o bug é da regra ou da decisão.

Quando quiser deixá-lo mais interessante

  • Aleatório: if(randf() < 0.3) ele defende em vez de atacar.
  • Reativo: se a própria vida estiver baixa, defende.
  • Oportunista: se a vida do player estiver baixa, ataca com tudo.
Cuidado com a IA perfeita Um inimigo que sempre joga o melhor lance costuma ser chato, não difícil. O que diverte é o jogador conseguir prever e planejar — e um pouco de imprevisibilidade tempera isso.
11 · Prática

LIGANDO OS TRÊS BOTÕES

A interface manda a intenção; o árbitro decide se vale

BattleUI.gd
●●●
extends Control

@export var battle : BattleManager

@onready var buttons = [
    $Actions/Attack,
    $Actions/Defend,
    $Actions/Flee
]

func _ready() -> void:
    buttons[0].pressed.connect(battle.player_attack)
    buttons[1].pressed.connect(battle.player_defend)
    buttons[2].pressed.connect(battle.player_flee)

    battle.turn_changed.connect(_on_turn_changed)
    _on_turn_changed(battle.state)

func _on_turn_changed(new_state) -> void:
    var my_turn = new_state == BattleManager.State.PLAYER_TURN

    for b in buttons:
        b.disabled = not my_turn
Conectar um signal direto a uma função de outro Node pressed.connect(battle.player_attack) — sem função intermediária, sem _on_botao_pressionado. Quando a função já faz exatamente o que você quer, ligue direto.
Os botões num Array Guardando os três numa lista, desabilitar todos vira um for de duas linhas. É o Array do Módulo 2 aparecendo onde ele realmente economiza trabalho.
Chamar _on_turn_changed no _ready Mesmo motivo da barra de vida do módulo passado: o signal só dispara quando muda. Sem essa chamada inicial, os botões começariam no estado errado.
12 · Conceito

POR QUE DESABILITAR OS BOTÕES

A trava no código já protege o jogo. Isto protege o jogador.

✅ A trava no código

if(state != State.PLAYER_TURN): return garante que nada acontece fora da vez. O jogo nunca fica em estado errado, aconteça o que acontecer.

✅ Os botões apagados

Comunicam ao jogador que não é a vez dele. Sem isso, ele clica, nada acontece, e ele acha que o jogo travou ou que o clique não pegou.

Uma regra que vale para o resto da sua vida programando Impedir no código e comunicar na interface são duas coisas diferentes, e você precisa das duas. Só a trava faz o jogo parecer quebrado; só o visual deixa o jogo quebrável.
"Mas ninguém vai clicar fora da vez" Vai sim. O jogador ansioso clica três vezes seguidas em atacar. Sem a trava, os três cliques valeriam e a batalha terminaria num turno.
Teste você mesmo Comente a linha do disabled e martele o botão de atacar durante o turno do inimigo. Depois comente a trava e faça o mesmo. Os dois defeitos são bem diferentes — e os dois são ruins.

14 · Prática

ACABOU. E AGORA?

Três finais, e o mesmo signal para os três

  Vitória

O inimigo caiu. Momento natural para soltar itens no chão, dar experiência, ou voltar ao mapa.

  Derrota

Tela de fim de jogo, ou voltar ao último ponto seguro — a mesma decisão do buraco, no módulo passado.

  Fuga

Volta ao mapa sem recompensa, com a vida que sobrou. O inimigo continua lá.

Quem escuta decide Pela terceira vez no curso: o BattleManager emite battle_ended("victory") e não faz mais nada. Quem trocar de cena, quem der a recompensa, quem mostrar a tela — é outro. O árbitro só apita.
Uma ideia para depois A recompensa da vitória pode ser um ItemData do Módulo 9, guardado num @export do inimigo. Aí cada inimigo dropa o seu — e você não escreveu um if sequer.
15 · Conceito

O QUE FAZ UMA BATALHA SER INTERESSANTE

O código está pronto. O jogo, não — isso depende dos números.

❌ A batalha sem escolha

Se atacar é sempre a melhor jogada, o jogador vai clicar em atacar até acabar. Três botões viram um botão só, e o turno vira espera.

✅ A batalha com dilema

Quando defender às vezes salva, e fugir às vezes é a jogada certa, o jogador precisa ler a situação. É aí que o turno começa a valer o tempo dele.

Vida ÷ danoDefine quantos turnos a luta dura. Menos de 3 é rápido demais; mais de 15 cansa.
Chance de fugaAlta demais, todo mundo foge. Baixa demais, ninguém tenta.
Redução ao defenderMetade é o padrão. Muito mais que isso e defender vira a única jogada.
Jogue a sua própria batalha dez vezes Se você se pegar clicando sempre no mesmo botão sem pensar, o problema não é o código — é o balanceamento. E ele se ajusta pelo Inspector, sem abrir script nenhum.

Estado controla o que o jogo aceitaUma variável decidindo quais ações valem — a ideia mais reaproveitável da aula.

O teste que a arquitetura passou A batalha inteira foi construída sem tocar no LifeComponent, na barra de vida ou no inventário. Um módulo novo, encaixado por cima, sem quebrar nada. É esse o retorno de tudo que você separou em componentes desde o Módulo 3.
As armadilhas de hoje checar a morte depois de passar a vez; esquecer de zerar o player_defending; esquecer o turn_changed.emit() em alguma troca de estado; e a divisão inteira transformando defesa em invulnerabilidade.
